# Contributing

`@choco-vanille/ui` is a React component library, not an application.
Contributions target v2 while preserving existing behavior and unrelated local
changes; updating this guide does not migrate the existing library.

## Source of truth

Use the repository's choco-vanille skill
for every library contribution. Its references own the detailed conventions;
this page is an orientation guide, not a second specification.

| Reference | Scope |
| --- | --- |
| Contribution | Scope, workflow, documentation and TypeScript |
| Architecture | Categories, imports, public API and distribution |
| Components | Anatomy, React contracts, composition and accessibility |
| Styles | Primitive props, Vanilla Extract, tokens and cascade |
| Quality | Code quality, semantics and consumer snippets |
| Tests and Storybook | Verification, controls, examples and documentation |

Read Contribution first, then the references relevant to the change.
Update the responsible reference when a convention changes instead of
maintaining another detailed copy here.

## Library organization

Public components live in `src/components/<category>/<component-name>/`,
classified by responsibility rather than by their technical dependencies.

| Category | Responsibility |
| --- | --- |
| `actions` | Actions and toggle controls |
| `data-display` | Data and content presentation |
| `feedback` | Status, progress and notifications |
| `forms` | Input, selection and editing |
| `foundation` | Core primitives, icons and typography |
| `layout` | Layout and visual structure |
| `navigation` | Navigation, orientation and step flows |
| `overlay` | Floating surfaces and contextual content |
| `surfaces` | Content containers and collapsible sections |

Theme contracts, tokens, providers and theme hooks belong in `src/theme/`.
Stories stay in `src/stories/`, tests in `tests/`, and Storybook configuration
in `.storybook/`. Stories and tests mirror the component category and folder.

## Target component anatomy

Use this structure for new components and explicitly requested v2 migrations:

```text
src/components/<category>/<component-name>/
  ComponentName.tsx
  ComponentName.css.ts
  index.ts
  types/index.ts
  constants/index.ts
  components/<child-name>/
  hooks/
  utils/
```

Only create files and folders that contain necessary code: styles, constants,
children, hooks and utilities are optional. Keep reusable elements under the
nearest common `_shared/<shared-element>/`, organized by cohesive feature.

Hooks and utilities follow the same ownership rule, recursively: use a
dedicated kebab-case folder only when they own types, constants or helpers,
with those resources in the corresponding subfolders. Simple component-local
hooks and utilities stay directly in `hooks/` or `utils/`, without an extra
per-function folder. See the Components reference for the detailed layout.

Existing `styles/`, `*.props.ts`, `*.types.ts` and `*.const.ts` files are legacy
layouts, not templates for new units. Migrate an existing unit's owned files
and imports together only when its migration is requested; do not clean up
unrelated components.

| Element | Target convention |
| --- | --- |
| Folders | `kebab-case` |
| Component implementation and styles | `ComponentName.tsx`, `ComponentName.css.ts` |
| Types and constants | `types/index.ts`, `constants/index.ts` |
| Hooks | `useComponentName.hook.ts` |
| Pure utilities | `resolveValue.utils.ts` |
| Stories and tests | `ComponentName.stories.tsx`, `ComponentName.test.tsx` |
| Re-exports | `index.ts` barrels only |

## Implementation priorities

Inspect the existing public contract and consumers before editing. Reuse
available primitives and helpers rather than adding speculative abstractions.
The current implementation establishes observable behavior, but it does not
override the v2 conventions.

Keep public props and unions independent of generated styles, and preserve
strict typing. Define types in `types/index.ts`, use `type`, `import type` and
readonly props, and expose consumer-facing symbols through the component,
category and package barrels.

Use Base UI for covered complex interactions and Vanilla Extract for styling.
Prefer supported visual primitive props before adding CSS, and use existing
theme tokens. Preserve native semantics, documented callback arguments,
consumer overrides, keyboard behavior, focus and theme scope.

Write English JSDoc beside components, hooks and utilities, including internal
ones. Document observable usage, defaults, accessibility, events and refs rather
than implementation history.

## Contribution workflow

1. Inspect local changes, define the requested scope and read the relevant skill references.
2. Trace the public API, owned styles, consumers, tests and stories; look for reusable code.
3. Implement the change without unrelated migrations, and adapt affected contracts, exports and consumers together.
4. Deliver behavior tests, accurate Storybook examples and directly affected documentation in the same change.
5. Run the applicable checks and inspect the diff. Report breaking changes, pre-existing failures and checks or visual reviews that could not be completed.

Keep component API examples beside their owner. Put introductory and
customization guidance under Overview, contributor guidance under Guidelines,
and theme, token and CSS variable references under Docs.

## Verification

Use **pnpm** and the configured tooling. Choose the smallest checks that prove
the changed contract; do not weaken types, lint rules or quality checks to
make a failure disappear.

| Change | Expected verification |
| --- | --- |
| Component | Targeted tests, types, lint, design-system audit and library build; Storybook build when stories change |
| Stories | Types, lint, Storybook build and targeted interactive review |
| Theme or styles | Affected tests, types, lint, library build and visual review of relevant themes and states |
| Distribution | Types, lint, library build and consumer checks for the affected formats or bundling behavior |
| Documentation only | Review content, metadata and links; no component tests or build unless executable content changes |

The skill lists the exact commands and required evidence for each workflow.
A successful build does not replace interaction checks or visual accessibility
review. Preserve ESM, CommonJS, declarations and the public CSS entry when
working on distribution, and never commit secrets or sensitive local settings.
