# Customizing the theme

Every token is a plain **CSS custom property** on `:root`, so you can re-skin the kit from **any** styling solution — plain CSS, Tailwind, Vanilla Extract, or even bridge the tokens into another component library like MUI. No rebuild required: override a variable and every component in that scope updates.

> Variable names are listed in **Theme / CSS Variables**.

---

## How it works in one minute

1. The kit ships a single stylesheet (`@my-org/ui-kit/styles.css`) that declares every token as a CSS custom property on `:root`.
2. Components read those variables — they never hard-code colours, spacing, or radii.
3. To customize, you **redefine the variable** in a scope (global `:root` or a scoped selector). The cascade does the rest.

This is a one-way contract: change the **CSS variable**, and every component in that scope follows. That single rule is what makes all the approaches in this section interchangeable.

---

## Pick the approach that matches your stack

Each method manipulates the **same** underlying CSS variables. Choose the one that fits your tooling.

| Page | When to use it |
|---|---|
| **Plain CSS** | Framework-agnostic, zero dependencies. Works everywhere. |
| **CSS Modules** | Component-scoped styles (Next.js, Vite, CRA) with kit tokens via `var()`. |
| **Tailwind** | You already use Tailwind and want kit tokens as Tailwind utilities. |
| **Vanilla Extract** | You want fully typed, autocompleted token access (the kit's own approach). |
| **Styled Components & Emotion** | CSS-in-JS template literals or object styles referencing kit tokens. |
| **MUI** | You also render Material UI components and want them to share the kit's tokens. |

---

## React integration layer: ThemeProvider

`ThemeProvider` is **not** an alternative customization method — it is a React convenience wrapper that sits **on top of** whichever CSS approach you already use.

It doesn't change how the kit reads tokens or how you override them. What it does:

- Manages the `data-theme` attribute on a wrapper element, or on `<html>` with `scope="document"` (the same attribute Plain CSS / Tailwind / Vanilla Extract all rely on).
- Follows `prefers-color-scheme` in `'system'` mode and updates reactively when the OS preference changes.
- Exposes a `setTheme` / `useTheme` hook so any React component can toggle the theme without touching the DOM directly.
- Accepts a `tokens` prop that injects CSS custom properties as inline styles — still the same CSS variables, just set at runtime instead of in a stylesheet.

In short: **you keep your existing customization approach unchanged; `ThemeProvider` only adds React state management around the `data-theme` attribute**. Its default document scope makes body-mounted portals inherit the application theme; use `scope="subtree"` for independent themed zones. Skip it if you manage `data-theme` another way (server-rendered attribute, a state manager, a URL param, etc.).

See the **ThemeProvider** page for the full API and usage examples.

## Important: the kit uses CSS cascade layers

The kit's token variables and reset styles live in named CSS layers:

<Source language="css" code={`@layer ${THEME_LAYER} { /* design tokens */ }
@layer ${RESET_LAYER} { /* box-sizing, body defaults */ }`} />

This means your overrides do **not** need to fight specificity. A normal unlayered rule in your own stylesheet will win over the kit's defaults, as long as it targets the same element. Keep your overrides outside any `@layer` (or place them in a layer you declare *after* the kit's layers) to guarantee they take precedence.

## Theme classes

The kit exposes two class constants for scoped theming:

| Constant | Value | Use |
|---|---|---|
| `THEME_DARK_CLASS` | `'${THEME_DARK_CLASS}'` | Force dark mode on any ancestor |
| `THEME_LIGHT_CLASS` | `'${THEME_LIGHT_CLASS}'` | Force light mode on any ancestor, even inside a dark scope |

Import them from the kit and use them in JSX or CSS selectors instead of hard-coding the class name.
